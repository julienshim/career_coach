# Changelog

Date + version (YYYY.MM.DD.N), newest first. One entry per commit that touches the mechanism, written at commit time, covering every mechanism change since the previous commit. N = that day's commit number. One line per change: what changed and why. Mechanism only — hats, standards, AGENTS, README, the registry contract. Instance changes are recorded in the hat logs and the ledger, not here. The entry is user-agnostic: the "why" names the class of failure a rule prevents, never an instance fact or inference (no dates beyond the entry's own version, no counts, no incident narrative). Uncommitted work lives in `git diff` and the hat logs; this file records what is in the commits. The design narrative — how and why the structure became what it is — lives in the README's How the System Evolved.

## 2026.11.24.1

- **Store (concurrency-safe derived state):** every connection arms a busy timeout, and the derived state (the status view, the full-text index) is rebuilt only when its definition or its indexed data changed — a hash guard in `meta`, the drop/create serialized under the write lock. Why: the every-open drop/create gave concurrent opens a window to interleave a drop with another connection's create — the system of record crashed under the mechanism's own parallel-batch rule, and a diagnosis made in a session that ended before it could be recorded left the same class to recur.
- **Store (application linking):** an event links to its application whenever the (company key, role) matches — neutral outcomes included — and the application is created only when the outcome sets a status; a one-shot `repair` op backfills the orphaned links (idempotent, the ledger export stays byte-stable), and the event→application edge enters the walk model (a walk stops cleanly at event rows). Why: an event whose outcome set no status was written outside the application's record — invisible to every application-scoped read while the one path that could see it was an op whose input format was not in the contract.
- **Store (last activity):** `status` carries the as-recorded date + type/outcome of the newest event of any kind — neutral included — beside the untouched status-setting derivation. Why: the status read could not answer what happened most recently.
- **Store (posting keying):** `job_opening` keys on company + title + link (the link is the duplicate key; the no-url form refuses a title carrying several postings, naming every link), and `log-event --url` upserts the posting and attaches it to the application in the same op. Why: the same title at the same company can carry several postings — a key that cannot tell them apart merges them.
- **Standards + hats (the contract carries the contract):** the flip prose names the complete neutral set and the assessment convention, the `query` ops row carries the minimal runnable plan (pinned to the `--example` output by a doc test), the ops rows for `repair` / `--url` / last activity are updated, the Company unit schema carries the companies.md boundary (the pre-check layer owns decisions / quirks / cap-usage; the dated history is the store's, and a standing-call line points at the store), and the sourcing hat's Step 0 matches the posting's link against the store's known postings before the fresh / different-role / re-apply call. Why: a vocabulary or an input format that lives in code, not in the contract, forces every cold session to re-derive it by source-archaeology, and a pre-check layer that cannot own its boundary drifts into the store's data.
- **Standards (diagnosed-defect rule):** a run that root-causes a mechanism defect ends with it recorded — a dated line in the mechanism's defect home, named in the run log's Next until the fix lands. Why: a diagnosis that dies with the conversation is a defect that will recur; the next session re-pays the diagnosis cost.
- **README:** the journal gains entry 13 — each defect class the audit found gets a fix in the shape of the class (the concurrent-open crash, the neutral-event orphaning, the undocumented input format), and entry 12's derived-state line is corrected to the conditional rebuild.
- **Tests:** new suites gate every class — concurrent opens (read ops + parallel writes + the rebuild's freshness), neutral-event linking / the repair / the cold-session acceptance, the flip vocabulary + assessment convention (doc pin + behavior), the posting keying (distinct links, the legacy refusal, upsert/attach), the query example (contract = flag = runnable), and the last-activity semantics; the existing status unpacks extended.

## 2026.11.20.1

- **Hats (lens/data separation):** the sourcing hat's resume call reads a skill's written-versus-oral depth and its written evidence ceiling from the resume unit's rules instead of asserting a person-specific resume fact the resume unit already owns — the hat points at the unit, it does not carry the unit's content. Why: a mechanism file that carries a person-specific fact is mis-scoped — the failure class is the lossy duplicate, which drifts the moment the evidence changes and tells the next agent the wrong file is the source of truth.

## 2026.11.19.4

- **Store (constrained query service, new):** the `query` op — a validated plan (an entity + filters + order + limit, up to three typed-junction traversal steps, or an FTS5 full-text search) executed on a structurally read-only connection against a double-gated whitelist (the entity / field / junction registry and the live schema); parameterized only — identifiers come from the registry and the live schema, every plan value is a bound parameter; capped (default 200, hard 1000 rows per stage); a JSON envelope reporting `rows_returned` / `rows_total` / `truncated` + the per-stage funnel; every result row carries `entity` + `id`. Rows / count / group modes over the root and the traversal path; the search resolves FTS5 matches to real entity rows ordered by rank. Why: an analytical question over related records had no bounded path — the failure class is the unbounded context pull, where a routine question balloons into an exhaustive sweep because nothing stops the retrieval from being unbounded, and a read that cannot be made read-only is a write waiting for a bug.
- **Store (derived full-text index, new):** the FTS5 `search_index` over the named text columns of the queryable entities — rebuilt at every open like the status view; it carries no contact email and no person row, and pointer columns are not searchable text. Why: keyword retrieval over the record was a grep over the files; the index as derived state cannot drift from the rows it indexes.
- **Standards + hats (retrieve first, then reason):** the store section gains the `query` op row and the invariants note (the analytical path is structurally read-only; the index is derived state); the execution rules gain the Explain rule — a recommendation names the record ids / EVIDs / document paths it rests on, a claim that cites nothing is invalid output, and a store-derived claim is labeled db fact / retrieved document / interpretation; the Analytical task class's context budget names the op (bounded, cited result sets); the strategy and sourcing hats retrieve cross-entity questions through it. Why: a recommendation that cites nothing is indistinguishable from an invention — the evidence-first rule extended to the query layer.
- **README:** the journal gains entry 12 — the constrained retrieval layer.

## 2026.11.19.3

- **Store (operational unification):** the operational layer is re-keyed onto the application entity — the ledger rows live in the `event` table keyed on `application.id` (append-only, raw rows verbatim), and the application's live status is the `v_application_status` view generated from the flip table at every open — no writable status column exists to drift. `log-event` creates or reuses the application for a status-setting event in the same atomic op; `status` / `caps` / `divergence` / `export-claim` / `export-ledger` and the fresh `migrate` read the new tables, with the status output unchanged from the previous model (as-recorded status date, the derived req, the live filter). Why: the operational layer was the loose-string model beside entities nothing could reach — an application could not be pointed at, and a derived status lived in a rebuilt table rather than a view no one can hand-set. Prevents the class of failure where two records of the same application coexist and a directive's scope points at a table with no entity behind it.
- **Store (one-shot migration, new):** `migrate-applications` upgrades a pre-unification db in one transaction: the ledger rows copied onto the new table with ids preserved, applications created for the legacy thread set, the application-scoped directives remapped onto the new ids (the scope ref renamed), and the ledger's raw rows verified byte-identical between the two tables before the legacy tables are dropped. Refuses a non-empty target; a clean no-op when the legacy tables are absent. Why: an in-place upgrade of the system of record must prove itself — the byte-stable third-party ledger is the acceptance criterion, and a verification mismatch rolls back with the legacy tables intact.
- **Store (operational entity ops, new):** `upsert-contact` / `upsert-job-opening` / `upsert-application` (create-or-verify on the natural keys, ungoverned; the target company — and the application's contact — must exist, and the op names the missing row instead of auto-creating it), `interview` + `set-interview` (rounds keyed on application + round; the status is provided at creation only, and `set-interview` is the only status mutation), `add-interaction` (insert-only). Why: the application workflow — who, which opening, which round, what happened — had no typed record; it lived in dated event text that nothing could query.
- **Store (working-set re-key):** application-scoped directives scope to the application entity (the legacy scope ref type leaves the enum; the op takes `--application-id`), and the dead-scope drift check reads the derived status view — a directive's application is gone, or its derived status is rejected / closed. Why: a scope pointing at a table with no entity behind it is a dead reference the drift scan must be able to name.
- **Standards + hats (the prose re-key):** "thread" in the store-entity sense is "application" in the shared rules and all six hats (the derived status, the application hub, the working set scoped by hat + application); the store section names the new tables, the new ops, and the one-shot migration; the registry contract names the new schema. Why: the mechanism's vocabulary had to follow the model — a standard naming a table that no longer exists is a dead reference in the contract itself.
- **README:** the journal gains entry 11 — the operational unification.

## 2026.11.19.1

- **Store (knowledge layer, new):** the schema gains the career knowledge layer — the person / company / role / project / skill / achievement / evidence / document entities, nine typed junction tables carrying the relationships, and the `instruction` table (scoped, expiring directives). Additive: a pre-existing db upgrades by being opened; the existing events/threads/run_logs tables are untouched. Why: the markdown career-map was the only relationship store — a relationship was queryable only by grep, and a link an agent drew was indistinguishable from a fact the user stated. Prevents the class of failure where the knowledge a run reasons over cannot be queried, filtered, or governed.
- **Store (upserts, new):** eight create-or-verify ops (person, company, role, project, skill, achievement, evidence, document) over one shared helper, test-first. A re-run that contradicts the record is identified — the op names the key, field, stored value, and given value — and refused with nothing written; stored NULLs may be filled; a matching re-run is a no-op returning the same id. Prevents the class of failure where a contradicting re-run silently overwrites the record instead of surfacing the conflict.
- **Store (typed junctions + lifecycle, new):** `link` (a typed edge; endpoints validated against the junction's endpoint types, attrs validated per junction, duplicates refused) and `verify` / `reject` / `unlink` — `verify` is the only path from an ai-provenance row at `ai_suggested` to `user_verified`; reject and unlink mark `rejected_outdated` rather than delete. No silent promotion, no destruction: an AI inference is born flagged and only an explicit user op promotes it; history is kept, never destroyed.
- **Store (governance reads, new):** `governance` (every governed row at a given state — the approve/reject queue), `find-disconnected` (entities with no relationship at all), and `export-relationships` (the junction rows as a TSV with names resolved — regenerated atomically, never hand-edited).
- **Store (the connected walk, new):** `neighbors` — a bounded depth-1/2 walk around an entity over both sides of the junctions and the direct FK edges, deduped, each edge carrying its provenance and governance state. The connected record around an entity is a table, not a graph — a walk the agent can read in full instead of pulling the directory.
- **Store (instructions + the derived working set, new):** the `instruction` op (kind / scope / scope-ref enums validated before any write; a user row is `active`, an ai row `suggested` until the user's `verify-instruction`; a supersede is atomic with its insert), `withdraw-instruction`, and `working-set` — a run's live directives are the derived query (active, in-scope, unexpired), not prose carried in a log row. Prevents the class of failure where a directive is smeared across log prose — restated, drifted, re-applied out of scope or past its window; a directive is scoped and expiring by construction.
- **Store (the working-set drift check, new):** `working-set-drift` — restated (an active directive's body verbatim in a hat's latest `next`), dead scope (a thread-scoped directive pointing at a missing or dead thread), expired (window closed — the op's only mutation: a one-shot flip to `expired`). Exit 1 on findings, mirroring the divergence check. The structural backstop for the scoped-directive discipline: drift becomes a finding, not an assumption.
- **Standards + hats:** the ops table gains the new ops; the invariants gain the mark-never-delete rule, the explicit-promotion-only rule, and the PII-gate's scope (the ledger stays third-party-safe; the knowledge tables hold user data by design under the instance-local boundary); the working-set rule and the layering row move to the derived form (`run_log.next` names the current task and points at the working set — it never restates a directive); all six hats' Log step carries the pointer form.
- **Store (DDL fidelity):** the `job_opening.jd_ref` comment restored to the architecture doc's verbatim text — the review caught a drifted comment in an otherwise verbatim DDL.
- **README:** the journal (How the System Evolved) gains entry 9 — the knowledge layer and the derived working set.

## 2026.11.16.2

- **Standards (the execution rules):** new standards section — the task-class table (operational / analytical / creative / structural) fixing per class the context budget (what a run may pull) and the closed write-scope (what it may write), plus seven rules: classify before you pull; the budget is a stop, not a target; closed write-scope; operational never pulls the career-map; escalation is a suggestion, not an expansion; the anti-generalization rule (no scope-widening, no priority-to-prohibition, no invented restrictions); the scoped working set (a run applies only the last log row's directives whose thread is still live and whose window has not passed; a stale one is a question, not an enforcement). ## 2026.11.16.1

- **Store (export-ledger):** the ledger export now orders events by date (`date_iso`, with `id` breaking same-day ties) instead of by insertion order. Why: a backdated or late-confirmed event — recorded after a later-dated one — was landing out of chronological order in the exported ledger, so a derived file showed the record in the order it was written rather than the order it happened. The export is a rendering of the record; its order is the record's date order. The `events.id` comment now states insertion order for the store and date order for the export.

## 2026.11.08.3

- **Divergence (calibration):** the drift check's name matching is now bidirectional and scoped to the company part — a narrative file names a stored company when either contains the other, case-insensitive, on the line's company part (the text before the role separator), not the whole line. Naming drift (a company key's suffix or wrapper missing from the narrative, or vice versa) no longer reports as drift; a company sharing no name at all still does, and genuine gaps (an application with no Q&A section, a closed thread missing from the cast) keep reporting. The company-part scope also removes a false "named" where the name only appeared inside another company's role text or an ordinary word. Prevents the class of failure where the detector drowns in naming noise and the genuine gaps stop being findable.

Prevents the class of failure where a restated value drifts from its home and both copies circulate as current.
- **Standards (the state flip):** new operating rule — a ledger row for a state-changing event is incomplete until the same run flips every state-carrying file that names the thread (the QA status line, the strategy cast line, the company standing call, the thread hub's live state); the state files are derived from the ledger and updated in the run that writes the event, never in a later cleanup. Prevents the class of failure where drift accumulates silently between full audits.
- **Sourcing hat (Step 7, Log):** the Log step now names the state flip — every state-carrying file that names the thread is updated in the same run; a ledger row without it is an incomplete log (the canonical rule stays in the standards; the hat names it once, no restatement). Prevents the class of failure where the logging step ends before the derived state is flipped.
